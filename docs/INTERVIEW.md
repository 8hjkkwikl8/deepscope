# 面试讲解手册

这份文档把 DeepScope 拆成"30 秒介绍、2 分钟演示、5 分钟架构、常见追问"四部分。面试前建议先自己跑一遍演示模式，确保网络能访问 360 搜索。

## 30 秒版本

"这是一个多 Agent 深度研究系统。用户输入一个开放问题，Planner 把它拆成几个子问题，多个 Researcher 并行搜索、抓取原文、生成带编号的笔记，Critic 找证据缺口并触发补充检索，Writer 流式写出报告。我重点做的是三件事：用 SSE 把 Agent 的每个动作实时呈现出来；用统一的来源注册表和引用校验，让报告里的每条关键结论都能回溯到原文；以及一整套降级策略，保证搜索、抓取或模型任一步失败时任务还能继续跑完。没有 API Key 也能用内置演示模式完整演示。"

## 2 分钟演示脚本

1. **首页**（15 秒）：指出四个角色卡与"标准/深度"切换。说明没有 Key 时顶部会显示"演示模式"，搜索仍然真实执行。
2. **开始一个研究**（10 秒）：点示例"多智能体落地与 ROI"，点发送。不要等待，直接讲"现在后台已经开始并发了"。
3. **左侧时间线**（30 秒）：指出阶段进度、Agent 状态、实时事件。强调来源编号在检索时就已经分配，后续笔记和写作都复用它。
4. **报告生成**（30 秒）：观察 token 流式输出。指出完成后报告的引用 chip、右上角"有据率/来源数/用时"。
5. **点一个引用**（15 秒）：点击正文的 `[S1]`，界面跳到来源 tab 并高亮对应卡片，证明"不是一段无法追溯的生成文本"。
6. **收尾**（20 秒）：切到"研究笔记"展示结构化中间产物，打开"系统架构"弹窗，用一句话总结设计取舍："拓扑固定，所以没有上 LangGraph；自己写编排器换来事件模型和失败隔离的完全可控。"

如果面试官想看真实模型：打开设置，填入 Base URL / 模型 / Key，点"测试并保存"，再跑一次。Key 只在内存，不落盘。

## 5 分钟架构讲解

按"数据流 → 事件流 → 引用闭环 → 降级 → 取舍"讲，顺序不要乱：

1. **数据流**：HTTP 创建 run → `Orchestrator` 五阶段 → Planner 输出 JSON → 并发 Researcher → Critic → Writer → 引用清洗 → 落盘。
2. **事件流**：`ResearchRun` 是发布订阅总线，`emit()` 同时写事件数组和订阅者队列；SSE 端点先重放、再实时推送，前端用 `seq` 去重。`token` 不持久化，重连时由最终的 `report` 事件补齐。
3. **引用闭环**：`SourceRegistry` 用锁分配 `S1..Sn`，按 URL 去重；笔记要求 `source_ids`；Writer 只看到已注册来源；结束后清洗无效编号、算 `grounded_ratio`、追加参考来源；前端把 `[S#]` 变成可点击 chip。
4. **降级**：搜索五级回退、单页抓取失败跳过、单子问题异常隔离、流式失败回退非流式、模型 400 去掉 `response_format` 重试。强调"失败是常态，任务必须能跑完"。
5. **取舍**：为什么不用 LangGraph、为什么 SSE 不用 WebSocket、为什么 JSON 文件而不是数据库、为什么原生 JS。每个取舍都给出触发条件："如果出现人工审批/任意跳转，我会换成图编排；如果多用户，我会换 Postgres + 队列。"

## 常见追问与回答

**Q：这和直接让 GPT 写一篇报告有什么区别？**
A：三个区别。第一，过程可审计：检索、阅读、笔记、审阅、写作都是独立事件，能定位问题出在哪一步。第二，引用是结构化的：来源先注册再引用，写作后清洗和统计，不依赖模型"自觉"编参考列表。第三，失败可降级：搜索源、页面、单个子问题、流式输出都有兜底，不是一次请求失败就全盘皆输。

**Q：怎么减少幻觉？**
A：不能承诺消除，只能约束。提示词要求每个关键判断至少一个引用；Writer 只能使用已注册来源；结束后移除无效编号并计算有据率；来源卡片保留原文链接供人工核验。下一步会做 claim 级支持度判断，把"有引用"升级为"引用确实支持结论"。

**Q：为什么不用 LangGraph / AutoGen？**
A：当前拓扑是固定的四角色加一轮条件补充检索，用图框架会引入额外抽象，事件和状态反而不好控制。自己写的编排器约 200 行，每个调度决策都能解释。如果未来出现多轮反思、人工审批、任意跳转，我会改用图编排，这是触发条件。

**Q：SSE 断线怎么办？**
A：事件有自增 `seq`，SSE 的 `id` 也用它；前端维护 `seenEvents` 去重。重连时服务端重放非 token 事件，前端补齐缺失状态；`token` 不重放，因为最终会有完整 `report` 事件。服务端每 12 秒发 keep-alive，终态发 `stream_end`。

**Q：并发怎么控制？**
A：子问题 `Semaphore(3)`，抓取 `Semaphore(4)`；同一 URL 的抓取结果（含失败）缓存；每个子问题最多抓 `fetch_top_k` 个页面；来源按域名做多样化，单域最多 2 个，避免结果全来自一个站点。

**Q：怎么评测？**
A：两层。流程指标：成功率、用时、来源数、引用来源数、有据率、关键词覆盖，`eval/run_eval.py` 可复现。质量指标：目前没有冒充，README 明确说这是流程指标；下一步会加人工标注集与 LLM-as-judge，并做 claim 级事实核验。

**Q：最大的技术难点？**
A：不是调模型，而是状态一致性。比如流式渲染和最终报告之间存在竞态：最后一批 token 的节流渲染可能覆盖带参考来源的最终报告；我在 `report` 事件里取消待执行的渲染，并让 `done` 再兜底一次。还有并发下的来源编号去重、SSE 重连去重、抓取失败不影响其他子问题，这些都是实际踩过并修掉的。

**Q：如果并发量上来怎么办？**
A：当前是单机单进程，`RunManager` 把任务放在内存。生产化会把 run 放进队列（Redis/Celery 或独立 worker），状态落 Postgres，SSE 通过 Redis Pub/Sub 扇出；再加每用户配额、搜索源限流和结果缓存。前端不用大改。

**Q：安全上做了什么？**
A：抓取前做 SSRF 校验（协议、凭据、localhost、私网/回环/链路本地、DNS 解析后再校验），页面读取限 2.5MB；前端 Markdown 用 DOMPurify 清洗；设置页的 Key 只存内存、不回显、不写日志；下载只允许已生成的报告。

**Q：这个项目你独立完成的吗？**
A：如实说明即可。可以讲清楚自己负责的部分：编排器、事件协议、引用闭环、降级策略、前端交互与测试；如果使用了 AI 辅助编码，也可以坦诚说明，并强调自己做了架构决策、调试与验证（例如引用清洗、SSE 重连、渲染竞态都是实际调试出来的）。

## 简历写法（可直接改）

- 设计并实现多 Agent 深度研究系统 DeepScope：Planner/Researcher/Critic/Writer 四角色协作，支持并行检索、审阅补检索与流式写作，端到端可运行。
- 设计基于 SSE 的实时事件协议与前端时间线，支持断线重连、`seq` 去重与历史回放，完整呈现检索、阅读、笔记、审阅、写作过程。
- 建立引用闭环：来源统一注册 `S1..Sn`、笔记与写作强制引用、无效编号清洗、`grounded_ratio` 统计与参考来源自动追加，实现报告结论可回溯。
- 设计多级降级与失败隔离：搜索五级回退、单页/单子问题失败隔离、流式失败回退非流式；无 API Key 时提供可完整演示的 Mock 模式。
- 编写 17 个单元/集成测试与离线评测脚本，覆盖引用统计、SSRF 防护、并发去重、全流程与失败隔离。
